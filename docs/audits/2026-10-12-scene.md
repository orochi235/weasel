# Audit: the scene's recording, after the `scene.ts` split

What the audit ranked first, the second op system beside `core/ops`, is built: an undo entry holds the scene's own ops whichever way the edit was made. What is left is the smaller things the split left open.

## 1. Left open by the split

**Selection is still two stores.** `sceneSelection.ts` owns the scene's copy, and the scene subscribes its notifier to it, so every selection change still bumps `getVersion()` and re-renders every `useScene` host. Giving it a subscription of its own that callers can use is a public API change (`getSelection`/`setSelection`, `sceneSelectionStore`, `useSelection({ scene })`) and was not made. (E)

- A second store does hold the same ids. `useSelection` without `scene` keeps a local store, `CanvasView` builds its own, and `SceneCanvas` binds to the scene only when no `selection` prop is passed. `defaultCommitAdapter` branches between them. The history engine only ever snapshots the scene's copy. (E; I that undo then restores the wrong store.)
- Selection has three contracts: `HistorySelection {get,set}`, `SelectionStore {getSelection,setSelection,subscribe}`, and `SceneAdapterSelection`, which accepts either. `sceneSelectionStore` only translates one to another.
- `loadState` writes the selection filtered by membership only. It is in `docs/TODO.md`.

**`version` counts three things**: document changed, selection changed, and history stack changed (the facade's `clear`, `recordEntry`, `prune`, and `switchBranch` call `notify`). `untracked` seals the coalescing run when it moved, and a selection-only change trips that. (I)

**"Who is driving this edit" is still held in five more places** besides `editMode.ts`: `replaying` in `staleReplay.ts`, `collecting` and `captured` in `recorder.ts`, `bypass` in `lockGuard.ts`, `applied` in `appliedLog.ts`, and `arrivals` in `arrivalWindow.ts`. The scene's `replay` sets three of them, and the edit mode, in one line. (E)

**`removeLayer` still scans every node** for the ones on its layer. `nodesOnLayer` answers the same question in render order rather than insertion order, which would reorder the nodes inside the recorded `kit:remove` payload, so it was left. (I, from reading `removalClosure`; not run.)

**Writes that reach state without a recorded op (E):** `kit:add` run directly by construction, the function fields patched on after an add, `loadState`'s clears and layer reset, every selection write, and the selection narrowing inside `kit:remove`'s apply, which its revert does not undo.

## 3. Not determined

Since determined: nothing in draw calls `undo` or `redo` on its mode history or on a mode's journal, so an edit made in a mode is not reachable from `scene.undo` as itself.

- **Production callers of `scene.undo`, `scene.redo`, `scene.canUndo`, `scene.canRedo`, and `scene.history`.** The receiver-pattern counts were 5, 3, 1, 1, and 7, but the sites were not listed to rule out docs and types.
- **Selection as an undo step.** Whether a recorded batch holding only a `setSelection` op becomes an undo step, against the `getSelection` docs in `types.ts`. Lasso marks its op transient; paste, booleans, and `replaceWithPaths` were not traced.
- **Callers through other receivers.** The caller greps matched receivers named like `scene`; a destructured or renamed receiver would be missed for generic names (`get`, `add`, `move`, `batch`).
