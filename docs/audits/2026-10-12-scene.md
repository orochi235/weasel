# Audit: `packages/core/src/core/scene/scene.ts`

**The file is long mainly because it hosts a second op system beside the one in `core/ops`, plus the glue that keeps the two from double-recording.** Selection, the nine history convenience methods, and the construction/load path are the next largest things that have another owner.

The file is 1,057 lines; `createScene` is 59–1014. Line numbers are `scene.ts` unless a file is named. **E** marks something I read or grepped, **I** marks reasoning.

One limit: partway through, Bash began refusing every command (the session was moved to the worktree `.claude/worktrees/long-file-audit` and commands were rejected from the shared checkout). The caller sweeps ran before that; a few follow-up greps did not, and they are listed in (c).

## 1. Two op systems for one tree (the main finding)

Every tree edit has two recordable forms (E):

| Effect | Per-scene op (`registered` map, `makeOp` 260–280) | Global `Op` factory (`core/ops`, `registerOpFactory`) |
|---|---|---|
| set pose | `kit:setPose` (537) | `transform`, `arrange` |
| add / remove | `kit:add` (473), `kit:remove` (517) | `insert`, `delete` |
| reparent / reorder | `kit:move` (654, 669) | `reparent`, `reorder`, `moveToIndex`, `setChildOrder` |
| data / layer / layout | `kit:setData`, `kit:setLayer`, `kit:setLayout` | `setData`, `setLayer`, `setLayout` |
| dependsOn, units, layer stack | `kit:*` only | none |
| selection | none (engine snapshot) | `setSelection` |

The direct route is `scene.setPose(...)` → `executeAndLog` → a `kit:*` entry. Align, distribute, ungroup, `usePoseRun`, `bindRig`, d3, and `reconcileSpecs` use it.

The other route is `scene.applyBatch(ops, label, adapter)` → `op.apply(adapter)` → `sceneMutators` → the same `scene.setPose`. There the kit handler runs with recording switched off, and the outer op is what gets stored (374–387).

One undo stack therefore holds both kinds. CLAUDE.md's "prefer ops so changes are undoable" no longer separates them: both routes are undoable.

What exists only to reconcile the two (E for each line; I that the duality is the cause):

- **`suppressRecording`** (176) and its `executeAndLog` branch (326–331).
- **`bindOpToAdapter`, `bindOpToHistoryAdapter`, and `scene.setHistoryAdapter`** (124, 384, 163, 855–857). The engine was built with no adapter (141), so stored outer ops must carry one.
- **`scene.carry` and `carriedPoses.ts`** (210–213, 540–542, 126 lines). An outer op's inverse does not know what the adapter wrote beside it. In the direct route the same writes are plain `kit:setPose` entries.
- **Two stale-replay mechanisms in `staleReplay.ts`**: `skips` inspects kit payloads, `tolerant` catches `SceneMembershipError` around outer ops.
- **`rebuildOp`'s four branches** (153–164).
- **Two rollbacks around one call**: the engine's `applyAllOrNothing` (`history.ts` 450–467) inside `atomically` (380–387).

The two routes also behave differently:

- **Journals.** Only `applyBatchNow` consults the active journal (369). `executeAndLog` (325–343) and the facade's `apply`/`applyOps` (`historyFacade.ts` 88–104) never do, so a direct `scene.setPose` during an open journal lands on the scene's own stack. (E)
- **Coalescing.** A bare direct call goes through `history.applyOps` (341) and can coalesce. The same call that touches a layout container is rerouted into `scene.batch` (531), which ends in `recordEntry` (891) and never coalesces (`history.ts` 353–358). (E for each line; I for the combined effect.)
- **Nesting.** `applyBatch` inside `scene.batch` pushes its own entry mid-batch, ahead of the batch's entry. (I, from 386 and 891; `scene.test.ts` 1196–1210 covers only the notify count.)

Where it should live: one recorded form. The candidate is to make `applyBatch` a `scene.batch` that applies the outer ops and records the `kit:*` ops they caused.

What must be true first:

- The engine needs a way to record already-applied ops that still coalesces.
- Ops that write non-scene state (`setSelection`, `setPath`, `setText`, hand-rolled ops like the one at `scene.test.ts` 1201) need a home.
- `core/ops` must stay for non-scene adapters such as `arrayAdapter`.
- Serialized histories change shape, so `apps/draw`'s persisted history (`App.tsx` 133, 159) needs a break or a migration.

## 2. Things with another owner

**Selection** (129, 144, 222–223, 245, 800–805, 960, 1020–1028).

- The store is a copy of `createSelectionStore` (`packages/select/src/store.ts` 10–24) wired to the scene's document `version` and `listeners`. Every selection change therefore bumps `getVersion()` and re-renders every `useScene` host (803–804). The neighboring `overrides` docstring makes a point of not doing that. (E)
- A second store does hold the same ids. `useSelection` without `scene` keeps a local store (`useSelection.ts` 68–69), `CanvasView` builds its own (152), and `SceneCanvas` binds to the scene only when no `selection` prop is passed (353–358). `defaultCommitAdapter` branches between them (31–34). The history engine only ever snapshots the scene's copy (142–145). (E; I that undo then restores the wrong store.)
- Selection has three contracts: `HistorySelection {get,set}`, `SelectionStore {getSelection,setSelection,subscribe}`, and `SceneAdapterSelection`, which accepts either (`sceneAdapter.ts` 45–50, 158–159). `sceneSelectionStore` only translates one to another.
- The five write sites disagree. 144 and 803 filter through `reachable` and notify. 223 does neither. 245 filters without notifying. 960 filters by membership only, so `loadState` of a snapshot with a locked layer can leave a locked node selected, against `lockGuard.ts`'s "never holds a locked node, whoever writes it". (E for the lines; I for the bug.)
- The scene's real job here is narrower: drop removed and locked ids (`narrowSelection`), and hand the engine a store.
- Move: `scene.selection` becomes a `createSelectionStore` instance behind the reachability filter, with its own subscription. This is a public API change (`getSelection`/`setSelection`, `sceneSelectionStore`, `useSelection({ scene })`), and anything relying on scene subscribers firing on selection needs a second subscription.

**History convenience methods** (809–853).

- `undo`, `redo`, `canUndo`, `canRedo`, `historyEntries`, `historyIndex`, `jumpToHistoryIndex`, `serializeHistory`, and `restoreHistory` are a second spelling of `scene.history.*`.
- The facade's `undo`/`redo`/`goto`/`restore` are wired back to these scene methods (362–365), so the two halves of one feature sit in two files, each calling the other.
- Move: the bodies go into `historyFacade.ts`, and `scene.history` is the one pathway.
- Differences to preserve or drop deliberately: boolean returns, clamping in `jumpToHistoryIndex`, and string ids in `historyEntries`.

**Engine construction** (1, 141). The scene imports `createHistory` from `@weasel-js/history`, not core's wrapper (`core/ops/createHistory.ts`), which supplies the debug logger. The scene's engine is silent under `DEBUG=history`. (E)

**Layer methods** (674–691, 697–763, about 80 lines). The layer stack is document content, so it belongs on the scene, but the bodies belong in `layerStack.ts` beside `requireLayerIndex`. They touch none of the shared variables except through `executeAndLog`.

**Layout latch** (93–102, 608). `hasLayouts` is set by casting a `NodeFnField` and overwriting its `write`. A write hook belongs in `createNodeFnFields`, or the arrival window should own the latch.

**Override clearing** (503, 940). `removeMany` clears overrides before the op. Redo of a remove and undo of an add both delete nodes without clearing them (`kitOps.ts` 121–128, 133–144), which is the reused-id hazard the comment at 501–502 describes. Clearing belongs in the handlers, the way `narrowSelection` is. (E for the lines; I for the bug.)

**Belongs here, one line each:**

- The reads (404–438) and `incarnation`.
- `mintId`.
- The mutators' validation.
- `removalClosure`.
- `isLocked` and `unlocked`.
- `toJSON`.
- `subscribe` and `getVersion`.
- `registry` and `composition`, which are pass-through config.

## 3. Duplicate pathways inside the file

- **`applyConstructionSpecs`** (976–1005) repeats `add`'s validation and payload (444–472), minus locks and `fnKeysOf`.
- **`loadState`** (949–956) rebuilds the layer stack by hand. `createLayerStack` (`layerStack.ts` 23–36) has the same loop.
- **`sceneFromJSON`** (1050–1055) builds a throwaway stack that registers every layer, user layers included, as a system layer, then `loadState` wipes it.
- **The "bare layout edit" re-entry**, `if (… && bareLayoutEdit()) return scene.batch(label, () => scene.X(args))`, appears six times (457–462, 512–515, 529–533, 609–612, 643–646, 662–665).
- **Suppress-and-defer-notify** is written three times with three flush policies: 304–316 discards dirt, 374–400 merges it, 903–927 flushes it.
- **The listener flush loop** is written four times (233, 398, 896, 925).
- **`setLayer`'s DFS** (554–568) duplicates `descendants` from the store, which `move` uses at 637–638.
- **`removeLayer`** scans every node (723–726) though `order.nodesOnLayer` exists (438).

**Writes that reach state without a recorded op (E):**

- `runOp('kit:add')` in construction (994).
- `patchNodeFunctions` after add (475, 1003).
- `loadState`'s clears and layer pushes (942–956).
- Every selection write.
- `narrowSelection` from inside an op's apply, which its revert does not undo.

A limited grep found no direct node mutation outside the scene directory.

## 5. The seven shared variables

| Variable | Written at | Read at | What it really is |
|---|---|---|---|
| `batchDepth` | 307/312, 377/389, 865/882, 908/918 | 229, 193, 396, 862, 884, 923, 936 | Two things: notify deferral, and "am I nested" |
| `batchDirty` | 230, 308/314, 375–397, 895, 924 | 393, 396, 894, 923 | Part of the notifier |
| `version` | 228 | 74, 904/922, 969 | Three things: document changed, selection changed, history stack changed (the facade's `clear`, `recordEntry`, `prune`, and `switchBranch` call `notify`) |
| `currentBatch` | 863, 878, 887 | 332–335, 873, 885 | `batch`'s private state |
| `suppressRecording` | 306/313, 376/390, 905/921 | 193, 275, 326 | "Something else is driving" |
| `untrackedDepth` | 906/920 | 216 | The untracked subset of the above |
| `selection` | 144, 223, 245, 803, 960 | 143, 222, 800, 863 | See section 2 |

`suppressRecording` and `untrackedDepth` are two encodings of one three-valued mode: recording, engine-driven, or untracked.

The same question, "who is driving this edit", is also held in other modules:

- `replaying` in `staleReplay.ts`.
- `replaying` and `noting` in `carriedPoses.ts`.
- `bypass` in `lockGuard.ts`.
- `applied` in `appliedLog.ts`.
- `arrivals` in `arrivalWindow.ts`.

`replay` (321–323) sets four of them in one line. (E)

`version`'s overload leaks. `untracked` seals the coalescing run when `version` moved (922), and `stale.tolerant` reads it to decide whether an op wrote anything; a selection-only change trips both. (I)

## (a) Ranked by how much they shrink or simplify the file

1. Settle on one recorded op form. Removes `suppressRecording`'s main use, adapter binding, `carry`, `setHistoryAdapter`, half of `staleReplay`, and most of `rebuildOp` and `applyBatchNow`.
2. Move the nine history methods into `historyFacade.ts`.
3. Make selection its own store with a reachability filter and its own subscription.
4. Extract one notifier (`listeners`, `version`, deferral) and one edit-mode value, replacing the three suppress blocks and four flush loops.
5. Replace the six layout re-entries with one `edit(label, fn)` wrapper, which also collapses `executeAndLog`'s three branches toward one.
6. Give construction one path: `add`'s validation shared with `applyConstructionSpecs`, `loadState` reusing `createLayerStack`, and `sceneFromJSON` without the throwaway stack.
7. Move the layer methods into `layerStack.ts`.
8. Move override clearing into the kit handlers; replace the `hasLayouts` monkeypatch.
9. Use core's `createHistory` wrapper; reuse `descendants` and `nodesOnLayer`.

## (b) What would be left in `createScene`

- Build state, store, layer stack, lock guard, notifier, and selection store.
- Build the engine and the history facade.
- `edit(label, fn)` plus `batch` and `untracked` on top of it.
- Node mutators (`add`, `removeMany`, `update`, `setPose`, `setLayer`, `setDependsOn`, `setLayout`, `setUnits`, `move`, `reorder`), each as validate, build payload, record.
- Assemble the `Scene` object from reads, node mutators, layer mutators, `selection`, `overrides`, `history`, and serialization.

That is roughly 300–350 lines (I).
