# Audit: the scene's recording, after the `scene.ts` split

**`packages/core/src/core/scene/` hosts a second op system beside the one in `core/ops`, plus the glue that keeps the two from double-recording.** That is the one finding still unbuilt, and it is "One recorded form for a scene edit" in `docs/TODO.md`. Section 2 lists the smaller things the split left open.

## 1. Two op systems for one tree

Every tree edit has two recordable forms (E):

| Effect | Per-scene op (`opTable.ts`, registered by `kitOps.ts`) | Global `Op` factory (`core/ops`, `registerOpFactory`) |
|---|---|---|
| set pose | `kit:setPose` | `transform`, `arrange` |
| add / remove | `kit:add`, `kit:remove` | `insert`, `delete` |
| reparent / reorder | `kit:move` | `reparent`, `reorder`, `moveToIndex`, `setChildOrder` |
| data / layer / layout | `kit:setData`, `kit:setLayer`, `kit:setLayout` | `setData`, `setLayer`, `setLayout` |
| dependsOn, units, layer stack | `kit:*` only | none |
| selection | none (engine snapshot) | `setSelection` |

The direct route is `scene.setPose(...)` → `recorder.record` → a `kit:*` entry. Align, distribute, ungroup, `usePoseRun`, `bindRig`, d3, and `reconcileSpecs` use it.

The other route is `scene.applyBatch(ops, label, adapter)` → `op.apply(adapter)` → `sceneMutators` → the same `scene.setPose`. There the kit handler runs with recording switched off, and the outer op is what gets stored.

One undo stack therefore holds both kinds. CLAUDE.md's "prefer ops so changes are undoable" no longer separates them: both routes are undoable.

What exists only to reconcile the two (E for each; I that the duality is the cause):

- **Most of `outerOps.ts`**: `scene.carry` and `carriedPoses.ts`, the `arrange` and `carry` branches of the restore-time rebuild, and the wrapping in the `applyBatch` route. An outer op's inverse does not know what the adapter wrote beside it, where in the direct route the same writes are plain `kit:setPose` entries. Not all of it: `bindOpToAdapter`, `bindOpToHistoryAdapter`, and `scene.setHistoryAdapter` are also what lets an op that writes no scene state be replayed at all, since the engine is built with no adapter. `scene.setActiveJournalAccessor` is journal routing and is unrelated.
- **The `engine` driver in `editMode.ts`**, as `applyBatch` and the history facade's `apply` and `applyOps` use it. Undo and redo need it either way.
- **`stale.tolerant` in `staleReplay.ts`**, which catches `SceneMembershipError` around outer ops. `stale.skips` inspects kit payloads and stays.
- **Two rollbacks around one call**: the engine's `applyAllOrNothing` inside `atomically`.

The two routes also behave differently:

- **Journals.** Only `applyBatch` consults the active journal (`outerOps.ts`). `recorder.record` and the facade's `apply`/`applyOps` never do, so a direct `scene.setPose` during an open journal lands on the scene's own stack. (E, and pinned.)
- **Journals of another history.** The accessor may return a journal the scene did not open: draw's mode machine opens its journals on a `createHistory(scene)` of its own. Nothing of the scene's drives that journal's `undo`, `redo`, or `cancel`, so each stored op goes back through the adapter into `scene.setPose` as a fresh edit, and leaves an entry on the scene's stack. (E, and pinned.)
- **Coalescing.** A bare direct call goes through `engine.applyOps` and can coalesce. The same call that touches a laid-out container runs as a batch (`recorder.edit`), which ends in `recordEntry` and never coalesces. (E; `scene.notify.test.ts` pins it.)
- **Nesting.** `applyBatch` inside `scene.batch` pushes its own entry mid-batch, ahead of the batch's entry. (E, and pinned.)

### The design

`packages/core/src/core/scene/scene.recordedForm.test.ts` pins today's behavior; "pinned" below names a test there.

| | |
|---|---|
| Entry | The `kit:*` ops the edit caused, in the order they ran, and beside them any *foreign* op: one that made no scene write when it applied. A foreign op is stored as it was given, bound to the adapter of the call. |
| Engine | One optional member on `Op`, `caused?(): Op[]`. Once an op has applied, the entry records what `caused()` returns in its place: `pushOrCoalesce` flattens after `applyAllOrNothing`, and nothing else in the engine changes. |
| `applyBatch` | Still hands its ops to the engine, or to the open journal. Each is wrapped so that its first apply collects the kit ops the scene ran for it, and `caused()` returns them. The op that settles arrivals is wrapped the same way, and so are the ops given to `scene.history.apply`, `applyOps`, and a scene journal's `applyBatch`. Inside `scene.batch` the ops apply directly and join that batch's entry. |
| Coalescing | A caused kit op takes the key `<outer key>><kit key>`, and none when the outer op had none, so two batches merge when they do today. |
| Non-scene ops | The foreign ops above: `setSelection`, and anything hand-rolled. Nothing in `packages/` or `apps/` implements or emits `setPath` or `setText`. |
| Serialized | `scene.serializeHistory()` adds `form: 2` beside the engine's own `version: 1`. `scene.restoreHistory` and draw's `loadSceneHistory` drop a snapshot without it. |

**Why `caused` and not a `recordEntry` that coalesces.** A journal cannot be handed ops that already ran, so that route needs a second addition on `Journal`, and draw's journals are not the scene's to wrap. It also moves into the scene what the engine does for a batch today: sampling the selection before the ops run, skipping an all-no-op batch, eliding, and inverting the ops that ran before one that threw. With `caused` the engine keeps all of it, for the scene's stack and for any journal.

**`history.ts` is at its recorded size** (947 lines, a 508-line function), so the engine change comes with a split of that file.

**What goes:** `carriedPoses.ts` and `scene.carry` (a cascade's writes are plain `kit:setPose` ops in the entry), `stale.tolerant`, and the `arrange` and `carry` branches of `rebuild`.

**What stays, against the TODO entry's list:** the `engine` driver and the engine's rollback inside `atomically`, because the engine still applies a batch's ops the first time; `bindOpToAdapter` for a foreign op; and `bindOpToHistoryAdapter` with `scene.setHistoryAdapter`, which a restored foreign op has no adapter without.

### What it changes besides nesting

Each follows from storing kit ops, whatever the mechanism.

1. **Undo and redo stop calling the adapter.** Pinned: "replays through the adapter the batch was applied with". An adapter method that writes outside state beside its scene write loses that half on undo.
2. **A journal of another history stops replaying as fresh edits.** Pinned: "a journal opened on another history replays through the scene as fresh edits", and the cancel test after it. A stored kit op reverts in place. In draw, canceling or discarding a mode stops leaving `setPose` and `update` entries on the scene's undo stack. To keep the canvas repainting, a kit op applied with no scene driver open has to run as a replay step and notify.
3. **`touchedIds` loses a deleted node.** Pinned: "names the node a delete took in touchedIds". The engine reads `args.id` or `args.node.id`, and a `kit:remove` payload has neither, as a direct `scene.remove` has none today. Draw's mode machine reads `touchedIds` to decide a cached journal is stale.
4. **A foreign op that throws a membership error on replay is no longer skipped**, once `stale.tolerant` goes. Not pinned: no such op is known.
5. **Two batches with the same outer keys that cause different kit ops stop merging.** Today they merge, and the undo restores only what the first one wrote.

### Rulings, 2026-10-12

- 2 is wanted: a mode's undo and cancel revert in place and leave nothing on the scene's stack.
- A restored foreign op keeps `setHistoryAdapter`, so undo still restores it after a reload.
- A direct scene call made while a journal is open stays on the scene's own stack.

## 2. Left open by the split

**Selection is still two stores.** `sceneSelection.ts` owns the scene's copy, and the scene subscribes its notifier to it, so every selection change still bumps `getVersion()` and re-renders every `useScene` host. Giving it a subscription of its own that callers can use is a public API change (`getSelection`/`setSelection`, `sceneSelectionStore`, `useSelection({ scene })`) and was not made. (E)

- A second store does hold the same ids. `useSelection` without `scene` keeps a local store, `CanvasView` builds its own, and `SceneCanvas` binds to the scene only when no `selection` prop is passed. `defaultCommitAdapter` branches between them. The history engine only ever snapshots the scene's copy. (E; I that undo then restores the wrong store.)
- Selection has three contracts: `HistorySelection {get,set}`, `SelectionStore {getSelection,setSelection,subscribe}`, and `SceneAdapterSelection`, which accepts either. `sceneSelectionStore` only translates one to another.
- `loadState` writes the selection filtered by membership only. It is in `docs/TODO.md`.

**`version` counts three things**: document changed, selection changed, and history stack changed (the facade's `clear`, `recordEntry`, `prune`, and `switchBranch` call `notify`). `untracked` seals the coalescing run when it moved, and `stale.tolerant` reads it to decide whether an op wrote anything; a selection-only change trips both. (I)

**"Who is driving this edit" is still held in five more places** besides `editMode.ts`: `replaying` in `staleReplay.ts`, `replaying` and `noting` in `carriedPoses.ts`, `bypass` in `lockGuard.ts`, `applied` in `appliedLog.ts`, and `arrivals` in `arrivalWindow.ts`. The scene's `replay` sets three of them, and the edit mode, in one line. (E)

**`removeLayer` still scans every node** for the ones on its layer. `nodesOnLayer` answers the same question in render order rather than insertion order, which would reorder the nodes inside the recorded `kit:remove` payload, so it was left. (I, from reading `removalClosure`; not run.)

**Writes that reach state without a recorded op (E):** `kit:add` run directly by construction, the function fields patched on after an add, `loadState`'s clears and layer reset, every selection write, and the selection narrowing inside `kit:remove`'s apply, which its revert does not undo.

## 4. Not determined

Since determined: nothing in draw calls `undo` or `redo` on its mode history or on a mode's journal, so an edit made in a mode is not reachable from `scene.undo` as itself. What the scene's stack does get is the entries a canceled or discarded mode leaves, in section 1.

- **Production callers of `scene.undo`, `scene.redo`, `scene.canUndo`, `scene.canRedo`, and `scene.history`.** The receiver-pattern counts were 5, 3, 1, 1, and 7, but the sites were not listed to rule out docs and types.
- **Selection as an undo step.** Whether a recorded batch holding only a `setSelection` op becomes an undo step, against the `getSelection` docs in `types.ts`. Lasso marks its op transient; paste, booleans, and `replaceWithPaths` were not traced.
- **Callers through other receivers.** The caller greps matched receivers named like `scene`; a destructured or renamed receiver would be missed for generic names (`get`, `add`, `move`, `batch`).
