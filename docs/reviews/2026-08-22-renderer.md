# Renderer review, 2026-08-22

A correctness pass over `packages/core/src/renderer` — the WebGL2 renderer:
`draw.ts`, `WeaselRenderer.ts`, `solidBatch.ts`, the shaders, and the
mesh/texture/glyph caches. For anyone touching that code next. It answers
"what is wrong in there right now", and records what was left alone.

The class of bug hunted: GL state left dirty across draws, cache keys missing a
dimension of what they cache, resources leaked, invalidation that does not
happen.

## Fixed

**A vertex-colored stroke never applied the clip test.** Every other
fragment-producing draw calls `applyClipTest` before its `drawElements`; the
`vertexColors` branch of `drawPathStrokeUnclipped` did not, so it drew under
whatever stencil state the previous draw left. Two visible failures:

- As the first child of a clipped group it inherits `pushClip`'s
  `stencilOp(KEEP, KEEP, REPLACE)` with the clip bit still in `ref` and
  `stencilMask` back at `0xFF`, so it *writes* clip bits over its whole ribbon
  — including outside the clip. Later siblings are then clipped to the wrong
  region, and `popClip` only clears where the clip path covers, so the stray
  bits outlive the group.
- Drawn after a clipped group it inherits `popClip`'s `EQUAL` against a bit
  that was just zeroed, and vanishes.

**`GroupState` was never reset between frames.** `drawGroup` pushes and pops in
balance, but only when it returns. It throws deliberately past 7 levels of clip
nesting, and that throw propagates out of `render()` with every enclosing
group's frame still on the stack — so the *next* frame draws under a leftover
transform, alpha and color matrix, permanently. `render()` now resets the state
at the top of the frame.

**`dispose()` leaked the pattern-fill program.** It was missing from the list of
programs to delete. The dispose tests asserted `>= 5` deletes against 7
built-ins, which is why nothing caught it; they now assert exact counts.

**`GLTextureCache` applied a wrap mode on first upload only.** The header
asserted an id "is either a pattern tile or a shader texture, never both" —
nothing enforces that, and both go through the same `registerTexture` registry.
One handle used for a pattern fill and a shader uniform got whichever mode
reached it first: a clamped tile shows one stretched edge instead of tiling.
`upload` now re-applies the wrap when it differs from what the id holds, which
is correct because every caller uploads and binds adjacently.

**Re-registering a custom program orphaned the old one.** `registerProgram`
replaces the entry in dev (hot reload) without deleting the GL program it
replaced. Minor, but free to fix.

Every fix has a test, and each test was mutation-checked: the fix was broken
deliberately and the test confirmed failing, six for six.

## Not fixed

**Per-draw VAO churn in `drawTextGroup` and `drawTextDecorations`.** Each builds
a VAO and two buffers, draws, and deletes them. The image path's own header
measures that shape at 5.4 us per draw against 0.3 us for a ring of reusable
slots, so the cost is real and named — but converting text to a ring is a
change of a different size than this review, and it wants the perf gate to
land it.

**`drawShader` rebuilds `mat3.screenToClip` per draw** instead of taking the
frame-cached `projFor(ctx)`. One small allocation per custom-shader draw; left
alone because it is not a bug and the churn is not worth a diff.

**`drawPathFillStencil` and `drawPathStrokeStenciled` exit with `stencilMask`
at `0x01`**, where the clip ops restore `0xFF` and document that as an
invariant. Nothing currently depends on it — every writer of the stencil sets
its own mask first — so this is an asymmetry, not a defect.

**`GLImageCache` is keyed by source identity alone**, ignoring `repetition` and
the cache's minification mode. The same collision as the texture cache in
principle, but no caller passes `repetition` today (patterns go through
`GLTextureCache`), so there is nothing to collide. Worth revisiting if image
patterns ever route through it.

**`dispose()` does not free `GLImageCache` textures or `GLMeshCache`'s
persistent meshes**, and nothing drains `pendingDeletes` after dispose. All
three are already documented in the `dispose()` docstring as deferred; the
headless render-to-pixels path, which hands one long-lived context to many
short-lived renderers, is where they accumulate. Left as recorded, not
re-litigated here.

## Checked and sound

Worth writing down so the next reader does not re-derive it:

- The solid batch's ring, and `flushSolids`' closing `bindVertexArray(null)`.
  `drawShader` binds no VAO and configures attributes on whatever is current,
  so the unbind is load-bearing. Every other draw path also ends with it.
- Folding group alpha into staged vertex colors. Exact under an identity color
  matrix — `clamp(src.a * groupAlpha) == clamp(src.a) * groupAlpha` when both
  are in `[0, 1]` — and `stageSolid` only folds when the matrix is identity.
- The per-draw color VBO deleted after `bindVertexArray(null)`. GL keeps the
  buffer object alive while a non-current VAO still references it, so the
  persistent mesh VAO is left with a live orphan rather than a dangling one,
  and each later vertex-colored draw on that VAO releases the previous orphan.
- `SolidBatch.nextLargeSlot`'s buffer growth. `ARRAY_BUFFER` is global state so
  the vertex path needs no VAO; the element path binds the VAO first, because
  `ELEMENT_ARRAY_BUFFER` is VAO state.
- `pushRect`'s short-circuit for `kind: 'rect'`. `RectPath` carries no corner
  radius, so there is nothing for it to drop.
- The layout, stroke-ribbon, outline and outline-stroke caches. Each key covers
  what its value depends on, including the two that are easy to miss —
  `flattenTolerance` in the ribbon key, and the font generation counter in the
  layout cache.

## Visual gate

None of these fixes change pixels for content that was already drawing
correctly: four are lifetime or state-hygiene, and the clip fix only affects
vertex-colored strokes combined with clipping. Run `npm run test:visual`
anyway before merging — the clip fix is the one that could move a baseline, and
this review did not run that gate.
