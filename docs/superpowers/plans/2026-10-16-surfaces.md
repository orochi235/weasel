# One schema for panels, toolbars, and menus

**Status: in progress on branch `surfaces` (2026-10-16). Delete this plan when the branch merges.**

For whoever builds or reviews the branch. It answers: what one prefs schema has to express so that
the same subtree can be drawn as a panel, a toolbar, or a menu, and how WeaselDraw's megatoolbar
(`apps/draw/src/CommandBar.tsx`) moves onto it.

## The model

A **pref** is a node in a prefs schema (`PrefGroup` and its leaves, `@weasel-js/prefs`): the
definition of a thing a surface can show. What a surface draws for a pref is, informally, a
*control* (editable) or a *readout* (display-only). The types keep the pref names.

A surface is how a schema subtree is drawn:

| Node | Panel | Toolbar | Menu |
|---|---|---|---|
| group or section `as: 'menu'` (new) | titled box | button opening it as a menu | submenu |
| group `as: 'page' \| 'tab' \| 'panel'` | as today | button opening a popover (today: `BarPopover`) | submenu |
| `section` / `fragment` | heading over rows / inline | separated run / inline | rows between separators |
| `action` leaf | button row with icon and label | icon button | item: label, icon, shortcut, enabled, checked |
| `actions` leaf (new): every action in one registry group | one button row each | one button each | one item each |
| `boolean` | checkbox | toggle | checked item |
| `enum` | select | segmented / dropdown | radio rows |
| `number`, `color`, `paint`, `string` | field | field or popover | left out |
| any value leaf with `readout: true` (new) | value, not editable | value, not editable | disabled item showing the value, booleans and enums only |
| `label`, `separator` | as today | as today | disabled item, separator |
| `alias` | the leaf it points at | same | same |
| `object`, `list`, `map`, `union`, `field` | as today | popover | left out |

**The path is the binding.** Surfaces already read `values` and write through `onChange` by dotted
path (`Bar`, `PrefsForm`), so where a value lives is the host's business: a prefs store, the
selection, the view. No schema field names a source.

## Phases

1. **prefs** — `'menu'` joins `PrefGroupAs` and `PrefSectionAs`; `readout?: boolean` on value
   leaves; a new leaf kind `actions` (`{ kind: 'actions', group: string }`) naming a registry
   action group, added to `PrefKind` and every renderer's exhaustive switch.
2. **ui** — `Bar` draws an `as: 'menu'` group as a button opening the DOM menu (`MenuPanel`) and an
   `actions` leaf as one button per action; `<ActionBar group>` becomes a `Bar` over an `actions`
   leaf. Panels draw action leaves with icon and label once, and `readout` leaves display-only, in
   both surfaces.
3. **routing** — `MenuDef` holds `schema: PrefGroup` in place of `sections`; `resolveMenu` walks it
   per the table, reading booleans and enums through optional `values`/`onChange` on
   `MenuSources`. `MenuDefEntry` and `actionVariants` go (an action leaf for a parametric action
   already expands to its variants). `apps/draw/src/menus.ts` moves over.
4. **draw** — a list of surface assets replaces the fixed `PANELS` (`apps/draw/src/panels.ts`):
   each has an id, a label, a schema, and a pref choosing toolbar, panel, or menu, switched from
   its header. Toolbar assets draw in the top strip, panel assets in the right sidebar, menu
   assets as a menu button in the command bar. First off the megatoolbar: Path (the `path` and
   `anchors` groups), Pathfinder, Arrange (reorder, align, distribute, flip). New and Debug become
   menu assets. File, history, clipboard, and edit stay last.

Out of scope here: draw's non-action controls (Simplify, Offset, Corner shape) as custom prefs, and
collapsing variants into a split button.
